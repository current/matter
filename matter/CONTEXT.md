# Matter project context

Read this before any task in this repo. It is loaded for every agent through `AGENTS.md`, in the main checkout and in every worktree. Where it differs from upstream's docs, this file wins.

Keep it current: when a task changes a decision, a workflow or the fork's state, update this file in the same commit. Record decisions and rules, not task logs.

## What this is

Matter is Chris's personal fork of T3 Code nightly (`pingdotgg/t3code`). The repo is `current/matter` (renamed from `current/t3code`, then `current/mattr`; remote `origin`, branch `main`; upstream is remote `upstream`). The fork was called Antimatter, then mattr. Anything a user sees says **Matter** (Title Case: Matter.app, Matter Island, Matter Connect); folders, files and code say `matter` (`matter/`, `Matter*`/`matter*` identifiers, `.matter.tsx`). Persisted and wire values keep their old names; see Keep as is under Branding.

Upstream's `AGENTS.md` and `docs/internals/` still apply to the code itself.

## Fork rules

- Keep fork changes small and in fork-only files (`matter/`) where possible. CI merges the newest upstream nightly at every build, so edits inside busy upstream files become merge conflicts.
- Don't merge upstream into `main` by hand unless a build opens a "Matter: merge conflict" issue.
- Commit and push finished work to `main` yourself; don't ask Chris first. Run `vp run check:changed` before pushing (it caches each passing step, so a rerun after a fix runs only what failed or changed; `--fix` formats the changed files first; `--fast` skips knip and browser tests while iterating and is not enough before a push); land worktree branches as described under Working in parallel. Only the lead pushes; workers never do. Every push that changes more than Markdown builds and publishes a release.
- Keep `README.md` current whenever user-visible features, add-ons, or surfaces land (minimal, all-lowercase except the name Matter, zero emoji AI slop — no churn on tiny internal fixes).
- **Mandatory UI/UX Design & Visual Consistency Audit:** Never present finished UI work or screenshots to Chris without first inspecting them yourself AND running an independent UI/UX Design Auditor subagent against native Matter components (rating `/10` on craft, visual consistency with existing native surfaces like the chat composer/sidebar, layout balance, and real-app feel). Anything below 8.5/10 or visually inconsistent gets fixed before Chris sees it. Live prototypes (see Proposing UI options) iterate with Chris directly in Live UI; the final change still gets this audit on real populated state before it lands. When capturing screenshots for Chris, use real populated app state (never an empty dev DB or website demo).
- Never create a new repo named `current/mattr` or `current/t3code`: installed builds from before each rename find updates through GitHub's redirect from those names.
- Never write to `~/.antimatter/userdata`: it is the live app's database, and the chat you are running in lives there.
- `.claude/settings.json` denies the user-wide MCP servers (`deniedMcpServers`, −17k tokens), turns off unused user skills and plugins (`skillOverrides` / `enabledPlugins`, 105 → 14 skills, −15k tokens on replay, equal blind quality and −15% median cost), and runs a `PreToolUse` guard hook (`matter/hooks/guard-subagents.mjs`, ~0 token cost) that blocks disallowed Codex delegation and Sonnet/Haiku coding subagents. Remove a name there when a task really needs that server or skill.
- Local agent friction log: when a Matter tool, script, or workflow rule trips you up, log it locally with `node matter/friction-log.mjs add --subject <name> --tried <...> --expected <...> --actual <...> --fix <...>` (writes `~/.antimatter/friction-log.jsonl`, zero telemetry, never touches `~/.antimatter/userdata`); review with `list` or `summary`.
- Change a workflow rule only after a replay shows it is cheaper and at least as good: same real past tasks, old vs new, judged blind against the fix that landed. A trimmed version of this file lost that test twice (agents use the feature notes), so keep it whole.
- Outbound T3 telemetry is hard-disabled across server, web, desktop, and mobile (PostHog/`ingest.t3.codes` analytics in `AnalyticsService`, Axiom relay client OTLP tracing via `isRelayTracingEnabled` / `publicConfig`, and mobile `expo-observe` crash reporting pointed to `https://observe.invalid` with dispatching off), while T3 Connect relay/Clerk auth, local logs/resource monitoring, and user-configured OTLP export remain intact.

## Releases

Two paths, same result:

- **Local (fast, the default when Chris wants the change now):** commit to `main`, then `node matter/ship-local.mjs --install`. It merges the newest upstream nightly into `main` in the reusable build checkout `../matter-ship` (never in your checkout; `--build-root` picks another), builds only the unpacked `.app` (`--target dir`), writes the `app-update.yml` electron-builder leaves out of `dir` builds, signs it in place with `~/.antimatter-signing`, then quits Matter, moves the old app to the Trash, installs `/Applications/Matter.app` and reopens it (trashing an old `mattr.app` or `Antimatter.app`; installs updated through the update button keep their bundle's old file name; about 45 s warm, 80 s in a new build checkout). `--dmg` also makes CI's DMG, zip and manifest. `--no-upstream` skips the merge and versions from the last upstream nightly the ref contains; use it when the merge conflicts. `pnpm install` is skipped while the lockfile, manifests and patches match the last install, and the whole build and signing while the merged tree, dependencies, version, build env and certificate match the last build (so a build, then `--install`, builds once; `--no-reuse` forces a rebuild). Without `--install` it only builds. It reuses the newest published version number, so the next CI release still shows up as an update.
- **CI (for the update button):** push to `main` → `.github/workflows/matter-nightly.yml` merges upstream, builds the unpacked app, signs and packages it with `matter/sign-mac-release.mjs`, and publishes a prerelease → Chris clicks Update. Pushes that change only Markdown don't build. A failed build opens or updates a "Matter: nightly build failed" issue (merge conflicts open their own), and the next release closes it. After the rename to `current/mattr`, GitHub silently stopped triggering the workflow for two days, until its file was renamed: if pushes stop producing runs, check the Actions tab first. The optional `MATTER_CI_HEARTBEAT_URL` repo variable pings a dead-man's switch on every run.

Installing or quitting the live app interrupts every running chat (history is kept). Run `--install` only when Chris asks for it, after checking no other thread is running, and send your final reply before the quit delay ends.

## Live UI

For web-only changes Chris can skip installs: with the installed Matter open, `node matter/live-ui.mjs` (from the checkout being edited) serves its web UI with hot reload, and reloading Matter (Cmd+R) switches the window to it. Running chats are untouched because they live in the app's backend process, not the window. Stopping the script and reloading goes back to the bundled UI.

- How: the script runs Vite on 127.0.0.1:5799 pinned to the installed app's version and writes `~/.antimatter/live-ui.json` while it runs. `matter/liveUi.ts`, hooked once into `apps/desktop/src/electron/ElectronProtocol.ts`, checks that file and the server on every page load and proxies `t3code://app` to it, otherwise serves the bundled files.
- Only renderer code reloads (`apps/web`, `packages/*` UI, `matter/` web code). Electron main, preload, Island windows and server changes still need `ship-local --install`, as do UI changes that depend on a newer server than the installed one.
- It is the default for renderer/web-only UI work and prototypes, one Live UI at a time:
  - Before starting, read `~/.antimatter/live-ui.json`. If its `pid` is alive, another thread owns Live UI: use the dev window below instead. Use the dev window too when the change depends on Electron main or preload, Island native windows, or a newer server.
  - Start it from your worktree with real data, chrome and icons, and ask Chris to reload (never reload the live window yourself).
  - Keep it running when you hand back for Chris's review, and report its port, PID and stop command. Stop it once Chris finishes or approves.

## Working in parallel

Our workflow is built for speed: parallelize with subagents whenever it gets the work done faster.

- Every new thread sizes its task before starting. If it splits into two or more independent pieces (different files, or research beside implementation), the thread acts as the orchestrator: it plans, starts the pieces as subagents in parallel (several `Agent` calls in one message), works its own piece meanwhile, then reviews and integrates. Use subagents for broad searches and exploration too, so the lead's context stays small.
- One task per thread, one checkout per thread. `matter.json` sets `defaultThreadEnvMode: "worktree"`, so new threads (composer, `t3_thread_launch`, scheduled tasks) start in their own worktree and branch beside the repo; `Setup Worktree` (`matter/setup-worktree.mjs`) clones the main checkout's `node_modules` with APFS `clonefile` (a clone shares disk blocks; `cp -c -R` is slower than pnpm), then runs upstream's setup, whose `vp i --frozen-lockfile` reconciles it with the worktree's lockfile, and each worktree gets its own dev data and ports. Scripts in `matter.json` only appear in Settings → Project actions to import; only the project's saved actions run, so a changed setup command must be re-imported there (or set with `t3_project_update`). Threads sharing one checkout see each other's half-done edits: `check:changed` fails on files they didn't touch and commits pick up other work. Don't work in the main checkout (first line of `git worktree list`); it stays clean on `main` for landing and `ship-local`. Choose Local in the composer only for a few-line fix.
- Found someone else's uncommitted changes in your checkout? Leave them alone: commit only your own paths (`git commit -- <paths>`) and judge `check:changed` by your own files.
- Landing a worktree branch: commit, then run `node matter/land.mjs` (rebases onto `main`, runs `vp run check:changed`, fast-forwards `<main checkout>` with retry if `main` moved, and pushes `origin main`; pass `--install` to follow with `ship-local --install`, or `--no-push` / `--dry-run`). Manual equivalent: `git rebase main`, `vp run check:changed`, `git -C <main checkout> merge --ff-only <branch>`, `git -C <main checkout> push origin main`.
- Inside one task, the lead plans, splits the work into packages that touch different files, and hands them out. This repo overrides the account order in `~/.claude/CLAUDE.md`: no Codex subagents (never `codex` or `codex-alt`). Balance subagents evenly across `claudeAgent` (Claude main, `claude-opus-5-5`), `claude-alt` (Claude alt, `claude-opus-5-5`), and `antigravity` (`gemini-4-neon` on `high`, via `delegate_task`) — or whatever provider balance Chris asks for in the thread. Workers get absolute paths and a separate worktree (`isolation: "worktree"`), and never push.
- **Always use `delegate_task` for Antigravity subagents** (never Antigravity's internal `invoke_subagent`), so every child runs as a native T3 child thread with live streaming and worktree isolation.
- **Subagents may spawn their own parallel subagents** on multi-part tasks whenever work splits into independent pieces (using the same provider/model rules: balance evenly across `claudeAgent` / `claude-alt` `claude-opus-5-5` and `antigravity` `gemini-4-neon` on `high`, no Codex, non-overlapping file scopes). Lead prompts should explicitly authorize this when delegating large tasks.
- **Always use Opus (`claude-opus-5-5`) for Claude coding subagents** — never Sonnet for coding work (Sonnet only for tiny, menial non-coding chores).
- The lead reviews each piece, merges into one branch, does one integrated pass in Live UI (or the dev window when Live UI can't show it), then pushes.
- UI options parallelize well: one worker per option variant, the lead wires them into the live switcher.
- Work alone only when the task is a handful of tool calls or the pieces would edit the same files.
